# План реализации: что нужно сделать и какие скиллы применять

Рабочая карта по этапам ТЗ. **Источник истины — [`docs/SPEC.md`](SPEC.md)**, здесь не пересказ,
а раскладка: что на выходе каждого этапа, какие скиллы включать, что скиллы не закрывают
и пишется руками. Отклонения от буквы ТЗ (хостинг) — по решению владельца, зафиксированы
в [`CLAUDE.md`](../CLAUDE.md).

---

## 0. Главное про скиллы, прежде чем читать дальше

**Скилл — инструкция агенту в сессии разработки, а не модуль бота.** Ни один из 82
установленных скиллов не «подключается» к боту: бот — Python-процесс, он ходит в API сам.
Скилл либо заставляет агента написать нужный модуль правильно, либо даёт паттерн, который
переносится в код руками.

По степени применимости они делятся на три сорта, и в таблицах ниже это помечено:

| Метка | Что значит |
|---|---|
| **готов** | Можно применять как есть, ничего внешнего не нужно |
| **референс** | Полезен как образец API или архитектуры, но привязан к чужому стеку (MCP-сервер, Membrane CLI, свой раннер, OpenAI) — брать паттерн, не запускать |
| **платный** | Требует чужого аккаунта и денег; решение за владельцем |

Скиллов Membrane в репозитории 20 (`telegram`, `gmail`, `perplexity`, `firecrawl`, `railway`,
`docker-hub`, `flyio`, шесть скрейперов и прочие). Все они — **референс**: работают через
Membrane CLI и его авторизацию, для рантайма бота это лишнее звено. Ценность — описание
методов API.

## Этап 0. Окружение и деплой

### Что на выходе

- `Dockerfile` — multi-stage на `python:3.12-slim`, непривилегированный пользователь,
  Chromium с Playwright **внутрь образа бота** (отдельным сервисом не выносим — решение
  владельца по Railway).
- `docker-compose.yml` — только для локального запуска. В проде Railway собирает образ
  и запускает сервисы по отдельности, единого compose там нет.
- `.env.example` со всеми переменными из ТЗ и пустыми значениями.
- `bot/config.py` — всё читается из `.env`, ключей в коде ноль.
- `bot/texts.py` — все русские тексты, ни строки в хендлерах.
- `prompts/report.md`, `prompts/email.md`, `prompts/criteria.md` — **рабочие заглушки**,
  выдающие корректный JSON нужной структуры, с комментарием в шапке «временная версия».
- Бот отвечает владельцу в Telegram.
- Логи в файл с ротацией.
- Ежедневный `pg_dump`, 14 копий (у managed-базы Railway свои бэкапы, но они наш дамп
  не заменяют — если платформу придётся менять, нужен свой).
- **`docs/DEPLOY.md`** — пошаговая инструкция для человека, который Docker не открывал.
  Это deliverable этапа, а не строчка в README.

### Приёмка

Локально `docker compose up` поднимает всё; в проде деплой из гита прошёл и бот ответил
владельцу; отсутствие ключей Perplexity и Firecrawl не мешает запуску, только пишет
предупреждение в лог.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `docker-deployment` | Основной. Multi-stage на `python:3.12-slim`, non-root, healthcheck, compose с Postgres 16, `.env.example`, Makefile — практически готовый этап | готов |
| `docker-best-practices` | Секреты через BuildKit (не ARG!), пиннинг образов по digest, именованные тома, лимиты ресурсов | готов |
| `devops-engineer` | План деплоя и отката, явное подтверждение перед развёртыванием | готов |
| `docker-management` | Жизненный цикл, отладка падающего контейнера, таблица команд с шагом верификации после каждой | готов |
| `python-pro` | `config.py` с типами, mypy strict, конфигурация логирования, структурная обработка ошибок | готов |
| `review-logs` | Ротация логов по возрасту и размеру. Оценку через локальную Ollama отрезать, механика переносится | референс |
| `pipeline-blueprint` | GitHub Actions, если нужен CI на тесты и линт до деплоя | готов |
| `railway` | Справочник по API Railway (проекты, сервисы, переменные) | референс (Membrane) |
| `docker-hub`, `flyio` | Только если хостинг будут пересматривать | референс (Membrane) |

### Скиллы под `docs/DEPLOY.md` — отдельная связка

Все скиллы выше **агентские**: они заставляют Claude писать правильный Dockerfile.
Человека они не учат ничему, владельцу их читать бесполезно. Инструкцию **производят** эти:

| Скилл | Что даёт |
|---|---|
| `dev-guide-generator` | Главный. Четыре фазы: аудитория и её уровень → чеклист пререквизитов («обязательно знать» отдельно от «желательно») → OS-специфичные команды установки с проверкой результата → 5–10 шагов, каждый с верификацией → типичные ошибки → шпаргалка. Реальные ключи в вывод не попадают |
| `runbook` | Задаёт форму: каждый шаг — точная команда **и ожидаемый вывод**, а не проза. Новичку видно, совпало у него или нет |
| `documentation` | Быстрый старт до первого результата за 5 минут, шаги отката, пути эскалации |
| `user-guides` | Diataxis: отделяет туториал от справочника. Новичку нужен туториал |
| `doc-coauthoring` | Доводка текста вместе с владельцем |
| `eng-runbook` | Только `example.html` — готовая форма однодневного runbook (таблица алертов, блоки команд, чеклист «что делать, когда упало ночью»). Сам `SKILL.md` на китайском и описывает вёрстку, как инструкция агенту не годится |

### Пишется руками

Настройка Railway (managed Postgres, сервис Mathesar из готового образа на ту же базу,
переменные окружения), `pg_dump` с ротацией на 14 копий, сам текст `docs/DEPLOY.md`.

### Риск

Приёмка этапа раздваивается: локальная (compose) и продовая (Railway). Не считать этап
закрытым по одной локальной.

## Этап 1. Каркас и база

### Что на выходе

- Структура проекта из ТЗ (`bot/handlers`, `bot/services`, `bot/db`, `prompts/`, `tests/`).
- Alembic-миграции на восемь таблиц: `requests`, `suppliers`, `candidates`,
  `quote_requests`, `orders`, `blacklist`, `criteria`, `criteria_events`. Плюс `api_calls`
  из раздела общих требований — в схеме ТЗ её нет, но учёт расходов обязателен.
- **Два частичных уникальных индекса**: `suppliers_domain_uq` на `lower(domain) WHERE domain
  IS NOT NULL` и `suppliers_tax_uq` на `tax_id WHERE tax_id IS NOT NULL`.
- `db/repo.py` — весь SQL. Ни одного запроса в хендлерах.
- `/start` отвечает только владельцу (whitelist по Telegram ID).
- Mathesar подключён к той же базе и показывает все таблицы.

### Приёмка

Миграции применяются **и откатываются**, бот отвечает на `/start` только владельцу,
Mathesar показывает все таблицы.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `postgres-database` | Основной. Схемы, индексы, **upsert через `ON CONFLICT`**, частичные и GIN-индексы — совпадает с нашей схемой один в один | готов |
| `alembic-best-practices` | Чеклист опасных операций, ловит **пустой `downgrade()`**. ТЗ требует рабочего отката — это приёмка | готов |
| `postgres-migrations` | Идемпотентность миграций, `pg_trgm`, полнотекстовый поиск (пригодится на этапе 6) | готов |
| `postgres-pro` | `EXPLAIN ANALYZE`, включение расширений, VACUUM | готов |
| `python-pro` | Типизированные модели, mypy strict, dependency injection | готов |
| `async-python` | asyncpg, пул соединений, конкурентность | готов |
| `bot-developer` | Конечные автоматы для многоходовых диалогов **с защитой от гонок**, whitelist, rate limiting | готов |
| `pytest`, `pytest-patterns` | Фикстуры на тестовую БД, `tmp_path`, изоляция тестов | готов |
| `telegram` | Справочник по методам Bot API | референс (Membrane) |
| `nocodb`, `baserow`, `grist`, `postgrest` | Только если Mathesar решат заменить | референс (Membrane) |

### Пишется руками

Mathesar в Railway, aiogram 3 роутеры и middleware whitelist, таблица `api_calls`.

### Риск

**Поведение `UNIQUE` с NULL — тонкое место, а оба наших индекса частичные.** Скилл, который
это специально разбирает (`postgresql` от wshobson), в репозитории **не установлен** —
docs/skills.md его упоминает, но до установки дело не дошло. Проверять руками: два
поставщика без домена и без ИНН не должны конфликтовать, а `example.com` и `EXAMPLE.COM` —
должны.

## Этап 2. Проверка в реестрах — критичный этап

**Делается вторым, до поиска и до отчёта.** Именно он отличает систему от запроса
в Perplexity, и именно он может не заработать — лучше узнать сейчас.

### Что на выходе

`services/registry.py`, одна функция:

```python
def check_product(name: str, ru_number: str | None = None) -> RegistryResult
```

- **`elk`** (после 01.03.2025) — виджет на React, обычный скрейп вернёт пустую оболочку.
  Открыть `https://elk.roszdravnadzor.gov.ru/widget/`, снять в DevTools → Network реальные
  запросы к `/public-gateway/med-product/api/v1/...` и работать с JSON напрямую.
  **Firecrawl к elk не применять.**
- **`misearch`** (до 01.03.2025) — разобрать формат GET-параметров
  (`?q_mi_label_application=ФСР+2010/08183`) и парсить результат.
- **`unrega`** — отдельной функцией, по названию и держателю РУ. Негативный сигнал.
- Кэш в Postgres на 30 дней.
- Статус `unavailable` при недоступности реестра — **не** `not_found`.
- Тесты.

### Приёмка

По трём реальным изделиям (до марта 2025, после, несуществующее) функция возвращает
корректный результат из правильного реестра.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `requests` | Самый нужный здесь. `Session` + `HTTPAdapter` + `urllib3.util.Retry`, обязательный `raise_for_status()`, ретраи на 429/500/502/503/504, запрет `verify=False`, **таймаут всегда кортежем** `(connect, read)`. Ровно правило проекта «каждый внешний вызов с таймаутом и ретраем» | готов |
| `async-python` | Если клиент асинхронный (httpx/aiohttp): таймауты, отмена, ограничение конкурентности | готов |
| `pytest`, `pytest-patterns` | ТЗ прямо требует тесты на этот модуль. `parametrize` на три изделия, `pytest.raises` на `unavailable`, фикстуры с записанными ответами | готов |
| `postgres-database` | Таблица кэша с TTL 30 дней и upsert | готов |
| `python-pro` | `RegistryResult` как dataclass с явными полями, а не dict | готов |
| `client-reverse` | **Только если** gateway `elk` окажется за подписью запросов. Трассировка в DevTools, поиск, чем считается подпись. Брать как справочник | референс |

### Чего скиллы не дают

Всё содержательное: сами реестры Росздравнадзора, формат их ответов, парсинг. Готового
скилла нет и не будет. Это ядро системы, пишется руками.

### Жёсткие запреты на этом этапе

- **Никакого LLM в модуле.** Только детерминированный код.
- **Подменять проверку реестра ответом модели запрещено при любых обстоятельствах.**
- `unavailable` ≠ `not_found`. «Не смогли проверить» и «не нашли» — разные строки в отчёте.

### Риск, который может изменить архитектуру

**Если gateway `elk` закрыт или защищён — остановиться и сообщить владельцу.** Не собирать
обходные пути молча. Варианты тогда: ручная проверка по ссылке в отчёте либо поиск выгрузки
открытых данных. Это решение владельца, не агента.

## Этап 3. Мультимодальный вход

### Что на выходе

`services/gemini.py`. Gemini берёт изображения и аудио нативно, отдельный Whisper не нужен.

- Фото → название изделия, производитель если виден, тип
- Голос → транскрипт
- Файл (PDF, docx) → описание изделия
- Текст → как есть

Выход всегда один: `{product, qty, requirements[], raw_input}`. Создаётся строка в
`requests` со статусом `search` и токеном `RFQ-{год}-{счётчик}`.
Отдельная команда: пересылка приложенного файла на `FORWARD_TO_EMAIL` через Gmail API,
без обработки.

### Приёмка

Фото коробки, голосовое и PDF дают одинаково пригодный `product`.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `firebase-ai-logic` | Ближайший к задаче: мультимодальный ввод (текст, изображения, аудио, видео, PDF) и структурированный JSON-вывод в одном месте | готов |
| `document-extract` | OCR и разбор структуры сканов, PDF и фотографий, отчёт по confidence. Под ветку «файл → описание изделия» | готов |
| `tutorial-generator` | Рабочий пример вызова Gemini Vision API из Python — как образец кода. Сам скилл про генерацию мануалов из скриншотов, интерфейс на японском | референс |
| `prompt-engineer` | Схема строгого JSON-вывода для распознавания, guardrails, оценочный набор | готов |
| `prompt-architect` | Что делать, когда на фото не разобрать изделие — явный fallback вместо выдумки | готов |
| `bot-developer` | Хендлеры приёма фото/голоса/файлов, состояние сессии | готов |
| `google-cloud-vision`, `cloudmersive` | Запасной путь для OCR, если Gemini не справится со сканами | референс (Membrane) |
| `gog-gmail` | Пересылка файла на `FORWARD_TO_EMAIL` | готов |

### Пишется руками

Приём голосовых в aiogram 3 и скачивание файлов через Bot API — готового скилла нет.
Транскрибация через Gemini — тоже: в каталоге такого скилла нет вовсе.
Генератор токена `RFQ-{год}-{счётчик}` с гарантией уникальности под конкурентными запросами.

## Этап 4. Поиск и скрейпинг

### Что на выходе

- `services/perplexity.py` — Search Query, ответ с источниками. **Вызов прямой, не через
  Membrane** (ТЗ явно: «выбери прямой»).
- `services/firecrawl.py` — по каждому кандидату: наличие позиции, цена, email, телефон.
  Firecrawl только для сайтов поставщиков.
- Каждый поставщик — в `suppliers` через upsert по `domain`/`tax_id`.
  **Матчинг по названию компании не делать**, названия пишут по-разному.
- Каждая проверка — в `candidates`.
- **Фильтр чёрного списка SQL-запросом ДО ранжирования и отчёта.** Заблокированный
  поставщик не попадает в выдачу вообще, даже с лучшей ценой.

### Приёмка

По одному запросу в БД появляется 5–10 кандидатов с заполненными контактами и результатом
проверки в реестре.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `perplexity-search` | Основной по поиску. Прямой вызов API, режимы `--search`/`--research`/`--reason`/`--deep` на моделях sonar, фильтры по свежести и доменам | готов |
| `research-agent` | Ровно наша задача «сайт поставщика → наличие, цена, контакты»: поиск URL → скрейп → извлечение полей в JSON, с валидацией по эталону и доводкой точности. **Но собран на SerperDev + gpt-4o-mini**, у нас Perplexity и Gemini — брать конвейер и петлю валидации, не код | референс |
| `firecrawl-scrape` | Минимальная обёртка: markdown/html/text. Запускается через Firecrawl MCP и чужой раннер — брать сигнатуры вызовов | референс |
| `seo-firecrawl` | `crawl`, `map`, `scrape`, рендер JS для SPA. Нужен, когда у поставщика большой сайт и надо найти страницу с нужной позицией | референс |
| `psycopg2-batch-insert-optimization` | Пакетная запись 5–10 кандидатов: `execute_values` вместо `executemany` плюс `ON CONFLICT DO UPDATE`. **Файл под MPL-2.0** — паттерн переносить, файл не форкать внутрь кода | готов |
| `postgres-database` | Upsert поставщиков, SQL-фильтр чёрного списка до ранжирования | готов |
| `prompt-guard` | **Важно.** С сайтов поставщиков в систему втекает недоверенный текст, который потом попадёт в промпт отчёта. Классификатор инъекций на входе | готов |
| `requests` | Таймауты и ретраи на Perplexity и Firecrawl | готов |
| `async-python` | Обход 5–10 сайтов параллельно с ограничением конкурентности | готов |
| `business-contact-social-links-skill` | Когда Perplexity дал название компании без домена: по названию находит официальный сайт и контакты | **платный** (BrowserAct, ключ в `BROWSERACT_API_KEY`) |
| `zenrows`, `scrapingbee`, `scrapingdog`, `zenscrape`, `scrapingbot`, `zyte-api` | Обход антибота вместо Botasaurus из ТЗ: прокси, геолокация, рендер | референс (Membrane), платные сервисы |
| `perplexity`, `firecrawl` | Справочники по методам API | референс (Membrane) |

### Пишется руками

Логика ранжирования кандидатов, извлечение ИНН с сайта, нормализация домена перед upsert
(`lower()`, срезать `www.`), учёт стоимости каждого вызова в `api_calls`.

### Риск

ТЗ предлагает Botasaurus как запасной вариант против антибота. В репозитории его нет и
скилла под него тоже — есть только платные сервисы-скрейперы. Если Firecrawl упрётся
в антибот, это отдельное решение по деньгам.

## Этап 5. Отчёт

### Что на выходе

`services/report.py`. Системная инструкция — в `prompts/report.md`, **читается с диска,
не хардкодится**.

Жёсткое требование: **LLM получает готовый JSON кандидатов и возвращает JSON. Рендер
сообщения делает код.** Свободный текст от модели не принимается — номера РУ и цены
поплывут не сразу, а на десятом прогоне.

По каждому поставщику **два независимых поля**:

- `РУ на изделие` — из реестра: номер, держатель, статус, какой реестр
- `Поставщик заявляет наличие` — с сайта: да/нет, ссылка

Плюс контакты (email и телефон **обязательны**, они нужны на этапе 6), цена если найдена,
флаги из `unrega`. Отчёт уходит в Telegram, статус заявки → `awaiting_choice`.

### Приёмка

Отчёт читается с телефона, **ни одно поле не смешивает данные реестра и данные сайта**.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `prompt-engineer` | Основной. Строгий JSON-вывод, function calling, гардрейлы, оценочные наборы — прямо под `prompts/report.md` | готов |
| `prompt-architect` | Превращает размытое намерение в проверяемую инструкцию, с явным fallback при отсутствии данных (нет цены, реестр `unavailable`) | готов |
| `prompt-guard` | Данные с сайтов поставщиков идут в промпт отчёта. Фильтр инъекций перед подачей в модель | готов |
| `python-pro` | Схема ответа как типизированная модель с валидацией, а не разбор dict вручную | готов |
| `bot-developer` | Рендер длинного отчёта в Telegram: лимит 4096 символов, разбивка, что показывать первым на телефоне | готов |
| `pytest`, `pytest-patterns` | Тест-сторож: поле реестра и поле сайта никогда не сливаются в одно. Это буквальная формулировка приёмки | готов |

### Пишется руками

Рендер сообщения из JSON (код, не модель), заглушка `prompts/report.md` до того, как
владелец даст настоящую инструкцию.

## Этап 6. Голосовой выбор и накопление критериев

Самый сложный этап после реестров — здесь система становится самопополняемой.

### Что на выходе

1. Gemini транскрибирует голосовое владельца («беру второго, потому что…»).
2. Вторая LLM по `prompts/criteria.md` извлекает структуру:
   `{критерий, направление, вес, к какому поставщику относился}`.
3. Пишем в `criteria` **с `ON CONFLICT` по смыслу**: если критерий уже есть — `times_seen + 1`
   и обновить `last_seen`. И в `criteria_events` — **вместе с сырым транскриптом**.
4. Накопленные критерии подмешиваются в промпт отчёта на следующих заявках.
5. Ветка «дай доп. информацию по поставщику, я ещё не выбрал» → повторный
   Perplexity/Firecrawl по одному поставщику → возврат в `awaiting_choice`.

Транскрипт хранить обязательно: через полгода странный критерий надо будет чем-то объяснить.

### Приёмка

После трёх заявок в `criteria` лежат осмысленные строки, а не пересказ голосовых.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `firebase-ai-logic` | Аудио на вход, структурированный JSON на выход | готов |
| `prompt-architect` | `prompts/criteria.md`: превратить «ну этот подороже, но привезёт быстрее» в проверяемую структуру | готов |
| `prompt-engineer` | Схема вывода и оценочный набор — как понять, что извлечение критериев не деградировало | готов |
| `recall` | Архитектурный образец «семантический поиск на PostgreSQL + BGE-эмбеддинги, режимы гибридный / только вектор / только текст». **Не готовый компонент**: это `/recall` над памятью самого агента, `user-invocable: false`, завязан на чужой раннер. Брать схему хранения и запрос | референс |
| `rag-architect` | Выбор между pgvector, Qdrant, Chroma и гибридный поиск Vector + BM25. Для нас ответ почти предрешён — pgvector на той же базе, новой инфраструктуры не заводим | готов |
| `postgres-pro` | Включение `pgvector`, индексы под векторный поиск, VACUUM | готов |
| `postgres-migrations` | `pg_trgm` и полнотекстовый поиск — дешёвый первый слой дедупликации до эмбеддингов | готов |
| `reasoningbank-agentdb` | Паттерны: трекинг траекторий, вердикт по исходу, **дистилляция памяти** (схлопывание похожих записей в один паттерн со счётчиком) — это ровно наш `times_seen` | референс |
| `agentdb-memory-patterns` | Разделение session memory и long-term storage | референс |
| `agentdb-vector-search` | HNSW-индексы, квантизация, пороги similarity | референс |
| `agent-memory`, `add-mnemon` | Та же линейка: как решают «уже видели такое или нет» | референс |
| `perplexity-research` | Для ветки «дай доп. информацию»: отдаёт **дельту** «что нового против уже известного», а не повтор того же | готов |

**Важно про три скилла AgentDB.** Им нужны Node.js, `npx agentdb@latest` (своя SQLite-база
векторов), регистрация MCP-сервера и OpenAI-эмбеддинги. Это против зафиксированного стека.
Ставить AgentDB как инфраструктуру — нет. Брать из них паттерны — да. Подробности
в [`.claude/README.md`](../.claude/README.md).

### Пишется руками

**Семантический `ON CONFLICT` по критериям** — самое сложное место этапа. «Срок поставки
важнее цены при разнице до 10%» и «лучше подождать, чем переплатить» — один критерий или
два? Ни один скилл этого не решает. Рабочий порядок: сначала точное совпадение, потом
`pg_trgm`, потом эмбеддинги с порогом, и **при сомнении заводить новую строку**, а не
склеивать: ложное склеивание испортит вес критерия навсегда, лишняя строка — нет.

Подмешивание накопленных критериев в промпт отчёта. Ветка «доп. информация вместо выбора».

## Этап 7. Письмо и ответ

### Что на выходе

**Отправка.** `prompts/email.md` → LLM формирует письмо → Gmail API отправляет на адрес
из `candidates`. Тема **обязательно** содержит токен: `[RFQ-2026-041] Запрос цены — <изделие>`.
Сохраняем `gmail_thread` и RFC `Message-ID` в `quote_requests`.

**Приём.** Опрос `history.list` раз в 3–5 минут. `users.watch` с Pub/Sub — потом, когда
заявок станет много.

**Матчинг ответа строго в этом порядке:**

1. `In-Reply-To` / `References` → `Message-ID`
2. `threadId`
3. токен в теме
4. адрес отправителя — **последним**, он ненадёжен: отвечают из общей почты, через
   секретаря, с личного ящика

При совпадении: уведомление в Telegram, текст ответа, все вложения файлами в чат.
Статус → `kp`.

### Приёмка

Письмо, отправленное **с другого адреса того же домена**, корректно привязывается к заявке.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| `gog-gmail` | Основной. 20+ команд: поиск, отправка, ответы, вложения, метки, **`history`**, сырой ответ Gmail API. Флаги `--readonly`, `--dry-run`, `--wrap-untrusted` | готов |
| `gmail` | 20+ операций, треды и вложения — второй справочник по API | референс (Membrane) |
| `gog-inbox-triage` | Санитизация тредов через `--sanitize-content --wrap-untrusted`. Сам писем не отправляет никогда | готов |
| `gog-save-attachments` | Обращается с каждым вложением как с недоверенным контентом — под пересылку файлов в чат | готов |
| `check-inbox` | Паттерн обёртки внешнего контента в `<external_untrusted_content>` | готов |
| `gmail-takip-sistemi` | Находит отправленные без ответа и готовит follow-up. Ложится на статус `silent` в `quote_requests` | готов |
| `prompt-guard` | **Критично здесь.** В систему втекают письма незнакомых поставщиков, и их текст идёт в LLM этапа 8. Классификатор инъекций на входе | готов |

**Матчинг по `In-Reply-To`/`References` — готового скилла нет ни одного.** Это наш код

### Риск

Тихая и дорогая ошибка: ответ привязался не к той заявке. Отсюда требование ТЗ — тесты
именно на этот модуль и на `registry.py`.

## Этап 8. Коммерческое предложение

### Что на выходе

1. LLM извлекает из письма позиции и цены в JSON под формат `assets/kp.example.json`.
2. **Показываем владельцу извлечённые числа на подтверждение в Telegram.** Цены приходят
   с оговорками («без НДС», «от 10 штук», «при 100% предоплате») — неверно вытащенная
   цена уйдёт клиенту **под вашей печатью**.
3. После подтверждения — `python scripts/build_kp.py --data kp.json --out ...`, PDF в чат.

### Приёмка

Из реального письма поставщика собирается КП с корректными суммами.

### Скиллы

| Скилл | Зачем | Сорт |
|---|---|---|
| **`kp-builder`** (в репозитории, `skills/kp-builder/`) | Главный и главнее остальных. **Его правила важнее удобства.** Читать `SKILL.md` целиком перед этапом, подготовка печати — `references/stamping.md` | готов |
| `pdf` | pypdf, pdfplumber, извлечение **таблиц**, OCR. Чего в kp-builder нет: поставщики присылают прайсы PDF-вложением, их надо читать | готов |
| `document-extract` | Если прайс пришёл сканом, а не текстовым PDF | готов |
| `prompt-engineer` | Схема извлечения цен **с оговорками как отдельными полями**: `vat_included`, `min_qty`, `prepayment` — а не одним числом | готов |
| `bot-developer` | Диалог подтверждения чисел в Telegram до сборки | готов |
| `geo-report-pdf` | Конвейер HTML → headless Chrome → PDF с автоматическими разрывами страниц — ближайший аналог нашего рендера | готов |
| `paper-poster-html` | Playwright print emulation и дисциплина «итерировать измерением, а не на глаз». Требует `Bash(*)` и MCP `codex`, которого в проекте нет, — фазы кросс-модельного ревью не отработают. Брать конвейер рендера | референс |
| `visibly-seo-pdf-build` | Запасной путь на fpdf2, если Chromium окажется тяжёл | готов |
| `apitemplateio` | Ещё один запасной путь | референс (Membrane) |

### Правила kp-builder, которые нельзя нарушать

- **Печать и подпись — только на финальной версии.** Черновик, «на посмотреть», вариант для
  обсуждения — всегда `--no-stamp`. **Автоматизацией это правило не обходить.**
- **Не выдумывать реквизиты.** Чего нет в `brand.json` и входном JSON — не подставлять.
- **Не генерировать печать и подпись.** Только реальные файлы из `assets/`.
- `valid_until` обязателен: нет — ставится +14 дней и владельцу об этом сообщается.
- Цена, похожая на ошибку на порядок, — повод спросить, а не промолчать.
- До первой сборки — `python scripts/check_assets.py`.

### Зависимости в образе

`jinja2`, `playwright` + `playwright install chromium`, `pillow`.
**Запасной WeasyPrint не поддерживает `mix-blend-mode`** — печать ляжет плоской,
для отправки клиенту не годится.

## Порядок и дисциплина

Этапы **0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8, строго по очереди**. У каждого свой критерий
приёмки. После каждого — показать владельцу работающий результат и **дождаться
подтверждения**, дальше не идти.

Две точки, где надо остановиться и спросить, а не решать самому:

1. **Этап 2, gateway `elk` закрыт или защищён.** Меняет архитектуру.
2. **Этап 4, Firecrawl не проходит антибот.** Botasaurus в репозитории нет, альтернативы
   платные — решение по деньгам.

## Замечание про количество скиллов

Скиллов установлено 82, и описания всех грузятся в контекст каждой сессии.
`docs/skills.md` сам это предупреждал: ставить по мере подхода к этапу. Если контекста
станет мало, чистку начинать с того, что помечено «референс (Membrane)» — их 20 и они
дублируют друг друга.
