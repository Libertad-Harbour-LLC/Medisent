# Medisent — память проекта

## Что это

Telegram-бот подбора поставщиков медицинских изделий: приём запроса (текст/фото/голос/файл) →
поиск поставщиков → проверка изделия в реестрах Росздравнадзора → отчёт владельцу →
голосовой выбор → письмо поставщику через Gmail → разбор ответа → коммерческое предложение в PDF.

**Полное ТЗ — [`docs/SPEC.md`](docs/SPEC.md). Это единственный источник истины.
Прочитай его целиком перед любой работой по проекту, не полагайся на пересказ ниже.**

## Стек (зафиксирован, не менять без владельца)

Python 3.12 + aiogram 3 · PostgreSQL 16 · Mathesar (веб-доступ к тем же таблицам) ·
Gemini API (мультимодальность) · Perplexity API (поиск) · Firecrawl (скрейп сайтов поставщиков,
запасной вариант Botasaurus) · Gmail API · скилл kp-builder (PDF).

Оркестрация — код бота. **Без n8n и без CRM.**

## Жёсткие правила

- **Деплой только на VPS с Docker Compose.** Serverless (Vercel и аналоги) не подходит —
  причины в ТЗ, раздел «Этап 0». Гибрид молча не собирать.
- **Реестров Росздравнадзора два, проверять оба:** `misearch` (до 01.03.2025) и
  `elk` (после 01.03.2025, через публичный gateway `/public-gateway/med-product/api/v1/...`,
  Firecrawl к нему не применять). Плюс `unrega` — информационные письма.
- **Никакого LLM в проверке реестра.** Только детерминированный код. Подменять проверку
  реестра ответом модели запрещено при любых обстоятельствах.
- **«РУ на изделие» (из реестра) и «поставщик заявляет наличие» (с сайта) — два независимых
  поля.** Сливать в одно «проверено в Росздравнадзоре» запрещено.
- Реестр недоступен → статус `unavailable`, не `not_found`.
- LLM отчёта и письма получают JSON и возвращают JSON; рендер сообщений делает код.
- Системные инструкции — в `prompts/*.md`, читаются с диска, не хардкодятся.
  `report.md` и `email.md` владелец задаст позже, пока — рабочие заглушки.
- Весь SQL — в `db/repo.py`. Ни одного запроса в хендлерах.
- Все тексты для пользователя — в `bot/texts.py`. Бот общается по-русски.
- Дедупликация поставщиков — только через уникальные индексы (`domain`, `tax_id`) и
  `INSERT ... ON CONFLICT`. Матчинг по названию компании не делать.
- Чёрный список фильтруется SQL-запросом **до** ранжирования и отчёта.
- Матчинг ответных писем строго в порядке: `In-Reply-To`/`References` → `threadId` →
  токен в теме → адрес отправителя (последним, он ненадёжен).
- Извлечённые из письма цены показываются владельцу на подтверждение до сборки КП.
  Черновик КП — с `--no-stamp`; печать и подпись только на финальной версии.
- Ключи только в `.env`; в коде и в git — ничего. `stamp.png` и `signature.png` — в `.gitignore`.
- Миграции через Alembic, откат должен работать.
- Каждый внешний вызов — с таймаутом, ретраем и учётом стоимости в таблицу `api_calls`.

## Порядок работы

Этапы 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 строго по очереди. У каждого в ТЗ свой критерий
приёмки. После каждого этапа — показать владельцу работающий результат и дождаться
подтверждения, дальше не идти.

Если на этапе 2 gateway `elk` окажется закрыт или защищён — остановиться и сообщить владельцу:
это меняет архитектуру.

## Скилл kp-builder

Распакован в [`skills/kp-builder/`](skills/kp-builder/). Перед работой с этапом 8 читать
[`skills/kp-builder/SKILL.md`](skills/kp-builder/SKILL.md) — **его правила важнее удобства
и важнее этой выжимки**. Подготовка печати и подписи — `references/stamping.md`.

Как устроено: JSON по формату `assets/kp.example.json` → Jinja2 + `assets/template.html`
→ рендер Chromium через Playwright → PDF. Реквизиты, цвета и геометрия печати — в
`assets/brand.json`.

```bash
python scripts/check_assets.py                              # до первой сборки
python scripts/build_kp.py --data kp.json --out "КП.pdf"    # финальная версия
python scripts/build_kp.py --data kp.json --no-stamp ...    # черновик
python scripts/build_kp.py --data kp.json --html-only ...   # посмотреть вёрстку
```

Правила скилла, которые нельзя нарушать:

- **Печать и подпись — только на финальной версии.** Черновик, «на посмотреть», вариант для
  обсуждения — всегда `--no-stamp`. Автоматизацией это правило не обходить.
- **Не выдумывать реквизиты.** Чего нет в `brand.json` и входном JSON — не подставлять.
  Пустое поле лучше правдоподобного вымысла в документе с подписью.
- **Не генерировать печать и подпись.** Только реальные файлы из `assets/`. Нет `stamp.png` —
  сказать об этом и собрать без печати, замену не рисовать.
- `valid_until` обязателен: нет — ставится +14 дней и владельцу об этом сообщается.
- Цены скрипт не проверяет, только считает суммы. Цена, похожая на ошибку на порядок, —
  повод спросить, а не промолчать (в боте это подтверждение цифр в Telegram до сборки).
- Позиционирование печати и подписи в `template.html` без причины не трогать.

Зависимости для контейнера `bot` (или отдельного `chromium` из ТЗ):
`jinja2`, `playwright` + `playwright install chromium`, `pillow` (для `check_assets.py`).
Запасной WeasyPrint не поддерживает `mix-blend-mode` — печать ляжет плоской, для отправки
клиенту не годится.

## Чего пока нет

- **`assets/brand.json` заполнен демо-данными автора скилла** (РИКО ДИЗАЙН, Буэнос-Айрес,
  `example.com`, НДС 21%). Это шаблон. До первой реальной сборки владелец заменяет его
  своими реквизитами — иначе КП уйдёт клиенту с чужой компанией в шапке.
- Ассеты `assets/logo.png`, `stamp.png`, `signature.png` кладёт владелец.
  `stamp.png` и `signature.png` в `.gitignore` — в репозиторий они не попадают никогда.
- Кода бота в репозитории ещё нет — записаны только ТЗ и скилл.
