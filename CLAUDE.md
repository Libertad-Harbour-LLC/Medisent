# Medisent — память проекта

## Что это

Telegram-бот подбора поставщиков медицинских изделий: приём запроса (текст/фото/голос/файл) →
поиск поставщиков → проверка изделия в реестрах Росздравнадзора → отчёт владельцу →
голосовой выбор → письмо поставщику через Gmail → разбор ответа → коммерческое предложение в PDF.

**Полное ТЗ — [`docs/SPEC.md`](docs/SPEC.md). Это единственный источник истины.
Прочитай его целиком перед любой работой по проекту, не полагайся на пересказ ниже.**

## Стек (зафиксирован, не менять без владельца)

Python 3.12 + aiogram 3 · PostgreSQL 16 · Mathesar (веб-доступ к тем же таблицам) ·
Gemini API (мультимодальность) · Perplexity API (поиск) · Firecrawl (скрейп сайтов поставщиков,
запасной вариант Botasaurus) · Gmail API · скилл kp-builder (PDF).

Оркестрация — код бота. **Без n8n и без CRM.**

## Жёсткие правила

- **Деплой только на VPS с Docker Compose.** Serverless (Vercel и аналоги) не подходит —
  причины в ТЗ, раздел «Этап 0». Гибрид молча не собирать.
- **Реестров Росздравнадзора два, проверять оба:** `misearch` (до 01.03.2025) и
  `elk` (после 01.03.2025, через публичный gateway `/public-gateway/med-product/api/v1/...`,
  Firecrawl к нему не применять). Плюс `unrega` — информационные письма.
- **Никакого LLM в проверке реестра.** Только детерминированный код. Подменять проверку
  реестра ответом модели запрещено при любых обстоятельствах.
- **«РУ на изделие» (из реестра) и «поставщик заявляет наличие» (с сайта) — два независимых
  поля.** Сливать в одно «проверено в Росздравнадзоре» запрещено.
- Реестр недоступен → статус `unavailable`, не `not_found`.
- LLM отчёта и письма получают JSON и возвращают JSON; рендер сообщений делает код.
- Системные инструкции — в `prompts/*.md`, читаются с диска, не хардкодятся.
  `report.md` и `email.md` владелец задаст позже, пока — рабочие заглушки.
- Весь SQL — в `db/repo.py`. Ни одного запроса в хендлерах.
- Все тексты для пользователя — в `bot/texts.py`. Бот общается по-русски.
- Дедупликация поставщиков — только через уникальные индексы (`domain`, `tax_id`) и
  `INSERT ... ON CONFLICT`. Матчинг по названию компании не делать.
- Чёрный список фильтруется SQL-запросом **до** ранжирования и отчёта.
- Матчинг ответных писем строго в порядке: `In-Reply-To`/`References` → `threadId` →
  токен в теме → адрес отправителя (последним, он ненадёжен).
- Извлечённые из письма цены показываются владельцу на подтверждение до сборки КП.
  Черновик КП — с `--no-stamp`; печать и подпись только на финальной версии.
- Ключи только в `.env`; в коде и в git — ничего. `stamp.png` и `signature.png` — в `.gitignore`.
- Миграции через Alembic, откат должен работать.
- Каждый внешний вызов — с таймаутом, ретраем и учётом стоимости в таблицу `api_calls`.
- **Отправка письма и пересылка файла идут без ретрая** (`retries=0`): повтор после
  таймаута отправит поставщику дубликат. Вместо повтора — проверка по своему
  `Message-ID`, который ставится до отправки.
- **Всё, что владелец подтверждает кнопкой, лежит в таблице `approvals`**, а не в
  памяти процесса. Отправка берёт адресата и текст из записи одобрения; перечитывать
  поставщика в момент отправки нельзя. Одобрение занимается одним `UPDATE` и живёт сутки.
- Уникальность пары «заявка + поставщик» в `quote_requests` держит база: второе письмо
  тому же поставщику по той же заявке не уходит.
- Потолок расходов **на заявку** (`MAX_COST_PER_REQUEST_USD`) проверяется до вызова, а не
  после. Дневной потолок остаётся мягким, как в ТЗ.
- Текст, пришедший из чужих рук, в промпт отчёта уходит в обёртке `guard.wrap_untrusted`.
  Названия компаний придумывает модель поиска по чужим страницам — это данные.
- Запрет «поставщик проверен в Росздравнадзоре» проверяется кодом
  (`report.scrub_conflation`), а не только инструкцией в промпте.

## Хостинг: решение владельца

**Railway — managed-платформа для контейнеров, не голый VPS.** Владелец выбрал её
вместо VPS из ТЗ (этап 0); Render рассматривался и отклонён: Docker остаётся, ssh, firewall, systemd и сертификаты —
уходят. Serverless (Vercel) отклонён, причины в ТЗ и подтверждены по актуальной документации:
на Hobby крон только раз в сутки, потолок функции 300 с, Mathesar там не запускается в
принципе.

Что это меняет в этапе 0 против буквы ТЗ:

- `docker-compose.yml` остаётся, но как инструмент **локального** запуска. В проде платформа
  собирает образ из `Dockerfile` и запускает сервисы по отдельности — единого compose там нет.
- `postgres` — не контейнер в compose, а managed-база платформы. `DATABASE_URL` приходит
  из её переменных. Заодно снимается противоречие ТЗ «PostgreSQL уже развёрнут» против
  контейнера `postgres`.
- `mathesar` — отдельный сервис платформы из готового образа, подключённый к той же базе.
- `chromium` — внутрь образа бота, отдельным сервисом не выносим.
- Приёмка этапа 0 раздваивается: локально `docker compose up`, в проде — деплой из гита
  прошёл и бот ответил владельцу.
- Ежедневный `pg_dump` (требование ТЗ, 14 копий) проверить отдельно: у managed-базы есть
  свои бэкапы, но они не заменяют наш дамп, если платформу придётся менять.

## Документация для владельца

**Владелец с Docker не работал ни разу.** Любая инструкция по запуску, обновлению и
развёртыванию пишется для человека без опыта контейнеров: каждый шаг — точная команда и
ожидаемый вывод, что делать при ошибке, никаких «просто поднимите compose». Это deliverable
этапа 0, файл `docs/DEPLOY.md`, а не строчка в README.

Подбор скиллов каталога AI Skills под все сервисы системы — [`docs/skills.md`](docs/skills.md),
раздел 13 про инструкции для новичка.

## Порядок работы

Этапы 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 строго по очереди. У каждого в ТЗ свой критерий
приёмки. После каждого этапа — показать владельцу работающий результат и дождаться
подтверждения, дальше не идти.

Раскладка по этапам — что на выходе, какие скиллы включать, что скиллы не закрывают и
пишется руками — в [`docs/PLAN.md`](docs/PLAN.md). Это рабочая карта, а не источник истины:
при расхождении с `docs/SPEC.md` прав ТЗ.

**Код этапов 0–8 написан.** Документы для владельца, по возрастанию детальности:
[`docs/HOW-IT-WORKS.md`](docs/HOW-IT-WORKS.md) — как работает бот без техники,
[`docs/TODO-LAUNCH.md`](docs/TODO-LAUNCH.md) — что осталось до запуска,
[`docs/DEPLOY.md`](docs/DEPLOY.md) — сами инструкции по шагам.

Что осталось непроверенным на живых данных: формат ответов реестров (правится в
`bot/services/registry_endpoints.py`, порядок описан в шапке файла) и первая сборка
Docker-образа.

Какие скиллы реально применялись при сборке и что от них осталось в коде —
[`docs/SKILLS-USED.md`](docs/SKILLS-USED.md). Каталог как таковой — `docs/skills.md`.

Аудит по чеклистам скилла `agents-best-practices` — [`docs/AUDIT.md`](docs/AUDIT.md),
что по нему сделано — [`docs/AUDIT-FIXES.md`](docs/AUDIT-FIXES.md). Все одиннадцать
пунктов закрыты.

Ревью кода после аудита — [`docs/REVIEW-PLAN.md`](docs/REVIEW-PLAN.md): 28 пунктов,
все сделаны семью коммитами. Что из этого стало правилами и надо знать при правках:

- Правило `found / not_found / unavailable` живёт в `registry.derive_state` и одинаково
  для реестров РУ и писем `unrega`. Состояние читается из `candidates.raw.registry.state`,
  из колонок его не восстанавливать.
- Порядок отчёта записывается в `candidates.raw.report.rank`; `list_candidates_for_report`
  сортирует по нему, и по нему же считается «беру второго».
- Любой id от модели сверяется со списком кандидатов (`criteria.extract`,
  `repo.is_selectable_candidate`) — чужой id не становится адресатом и не идёт в FK.
- Всё, что бот показывает владельцу и что пришло не из `texts.py`, проходит через
  `texts.esc`: бот в `parse_mode=HTML`, и одно `<` в чужом тексте ломает сообщение.
- Пара «заявка + поставщик» резервируется в `quote_requests` (`sending`, свой `Message-ID`)
  в той же транзакции, где занимается одобрение, и только потом идёт `send`.
- Курсор Gmail двигается после разбора всего среза; письмо читается сначала заголовками.
- Учёт расходов — только `http._record`; цена по токенам — через `price=` у `ApiClient`.
- Статус заявки меняется только через `repo.transition` по `ALLOWED_TRANSITIONS`;
  закрытие — `pipeline.close_request`.
- Системных инструкций в коде нет: `prompts/product.md`, `transcribe.md`, `extract.md`,
  `search.md`, `report.md`, `email.md`, `criteria.md`.

Если на этапе 2 gateway `elk` окажется закрыт или защищён — остановиться и сообщить владельцу:
это меняет архитектуру.

## Скилл kp-builder

Распакован в [`skills/kp-builder/`](skills/kp-builder/). Перед работой с этапом 8 читать
[`skills/kp-builder/SKILL.md`](skills/kp-builder/SKILL.md) — **его правила важнее удобства
и важнее этой выжимки**. Подготовка печати и подписи — `references/stamping.md`.

Как устроено: JSON по формату `assets/kp.example.json` → Jinja2 + `assets/template.html`
→ рендер Chromium через Playwright → PDF. Реквизиты, цвета и геометрия печати — в
`assets/brand.json`.

```bash
python scripts/check_assets.py                              # до первой сборки
python scripts/build_kp.py --data kp.json --out "КП.pdf"    # финальная версия
python scripts/build_kp.py --data kp.json --no-stamp ...    # черновик
python scripts/build_kp.py --data kp.json --html-only ...   # посмотреть вёрстку
```

Правила скилла, которые нельзя нарушать:

- **Печать и подпись — только на финальной версии.** Черновик, «на посмотреть», вариант для
  обсуждения — всегда `--no-stamp`. Автоматизацией это правило не обходить.
- **Не выдумывать реквизиты.** Чего нет в `brand.json` и входном JSON — не подставлять.
  Пустое поле лучше правдоподобного вымысла в документе с подписью.
- **Не генерировать печать и подпись.** Только реальные файлы из `assets/`. Нет `stamp.png` —
  сказать об этом и собрать без печати, замену не рисовать.
- `valid_until` обязателен: нет — ставится +14 дней и владельцу об этом сообщается.
- Цены скрипт не проверяет, только считает суммы. Цена, похожая на ошибку на порядок, —
  повод спросить, а не промолчать (в боте это подтверждение цифр в Telegram до сборки).
- Позиционирование печати и подписи в `template.html` без причины не трогать.

Зависимости для контейнера `bot` (или отдельного `chromium` из ТЗ):
`jinja2`, `playwright` + `playwright install chromium`, `pillow` (для `check_assets.py`).
Запасной WeasyPrint не поддерживает `mix-blend-mode` — печать ляжет плоской, для отправки
клиенту не годится.

## Инструменты разработки

В `.claude/` установлен [Skill Forge](https://github.com/AgriciDaniel/skill-forge) — конструктор
скиллов для Claude Code (9 скиллов + 8 субагентов, MIT). Это инструмент разработки, **к боту
и его рантайму отношения не имеет**, в `docs/SPEC.md` не входит. Происхождение, версия, команды
и порядок обновления — в [`.claude/README.md`](.claude/README.md).

Там же — 37 скиллов [Мэтта Покока](https://github.com/mattpocock/skills) (грилинг решений,
спека → тикеты → реализация, TDD, доменное моделирование, диагностика багов). Начинать с
`/ask-matt` — это роутер по набору. Один переименован: `code-review` → `/matt-code-review`,
потому что встроенный `/code-review` Claude Code перекрывал его и скилл не загружался; это
два разных ревью, оба рабочие. Пять скиллов набора завязаны на TypeScript и к нам не
применимы, а `git-guardrails-claude-code` ставит хук, блокирующий `git push` — вызывать
его в этом репозитории не надо. Подробности и оговорки — в том же `.claude/README.md`.

## Чего пока нет

- **`assets/brand.json` заполнен демо-данными автора скилла** (РИКО ДИЗАЙН, Буэнос-Айрес,
  `example.com`, НДС 21%). Это шаблон. До первой реальной сборки владелец заменяет его
  своими реквизитами — иначе КП уйдёт клиенту с чужой компанией в шапке.
- Ассеты `assets/logo.png`, `stamp.png`, `signature.png` кладёт владелец.
  `stamp.png` и `signature.png` в `.gitignore` — в репозиторий они не попадают никогда.
- **Оценочный набор на промпты есть, но на записанных ответах модели** — `tests/evals/`.
  Он стережёт инварианты (выдуманный id не проходит, `unavailable` не превращается в
  `not_found`, поля не сливаются), но не качество формулировок. Когда владелец заменит
  заглушки промптов своими текстами, к набору стоит добавить прогон на живой модели.
